# 分享几个 vibe coding 时的 prompt 技巧

# 

前言

大家好，我是大刀，最近频繁使用 vibe coding 做项目，有一个感受很明显：AI 写代码不是问题，问题是它很容易太快开始写，即没想好就开始写。一旦太快进入实现，就会出现问题，如方向还没对齐，但是代码已经写了一大堆；自己重复造轮子；还有过于复杂或者考虑不周全等问题。 在经历了多次项目复盘后，现在写 prompt时，会刻意加几道刹车，让它及时的停下来，思考清楚再动手。这里分享几个我自己在实际使用时常用的 prompt 技巧。希望对大家有用。

## 01 — 开新项目前，先让它去 GitHub 找相似项目

刚开始用vibe coding开发新项目时，会直接上手：

> 帮我做一个 XXX。

然后 AI 马上开始吭哧吭哧搭目录、写代码、造组件、配数据库。 这其实是很危险的，因为你不知道这个方向有没有成熟参考，也不知道别人是如何解决同类问题，更不知道这个需求里有哪些坑是前人已经踩过的。所以现在开新项目时，会先让 AI 先做一件事：

> 在 GitHub 上搜索相似项目，找 3 到 5 个有参考价值的仓库。  
> 分析它们的功能范围、技术栈、目录结构、核心实现方式、优缺点。  
> 不要写代码，先输出调研结论和我这个项目应该借鉴什么、避免什么。

这个 prompt 的核心不是抄代码，而是让 AI 先建立行业上下文。

vibe coding 最大的问题，不是 AI 不会写，而是它默认会从自己的知识里拼一个“看起来合理”的方案。但真实开发不是这样的，真实的开发一定要看上下文，类似于前置的先验知识：同类产品怎么做，主流实现是什么，哪些方案已经被证明不好用。而GitHub 上的成熟项目，相当于给 AI 一组现实样本。它看到这些样本后，生成的方案会更贴近真实工程，而不是凭空搭架子。

### 示例 prompt

> 在开始开发前，请你先去 GitHub 搜索相似项目，不要写代码。
>
> 请输出：
>
> 1. 找到的相似项目列表，包含项目地址、stars、最近更新时间、主要技术栈。
>
> 2. 每个项目解决了什么问题，核心功能是什么。
>
> 3. 它们的目录结构和关键模块设计有什么共性。
>
> 4. 哪些设计值得我们借鉴，哪些设计不适合我们。
>
> 5. 基于这些调研，给出本项目的 MVP 范围和技术实现建议。
>
> 要求：
>
> - 必须打开项目源码或 README 核对，不要只看搜索结果。
>
> - 不要直接照搬代码。
>
> - 如果没有足够相似的项目，要明确说明。

这段 prompt 很重要的一句是： 不要写代码。这其实是把调研阶段和实现阶段分开。这样AI 可以一开始在充分调研好后，再去实施。

### 工程注意点

第一，不要只让它看 stars。高 stars 不代表适合我们。很多项目只是概念火，代码并不适合生产。要看最近更新时间、issue 状态、目录结构、测试情况、文档完整度。

第二，不要让它直接复制架构。参考项目的目标用户、规模、历史包袱可能和我们完全不同。我们要的是借鉴决策，不是复制形状。

第三，调研结果要落到 MVP。很多项目一看就很大，AI 很容易被带偏，最后给你设计一个过重的系统。得基于追问：哪些功能必须做，哪些功能明确不做？

以上的操作才能帮我们把功能慢慢收敛回来。

## 02 — 开发时用剃刀原理和第一性原理

AI 写代码有一个偏向：喜欢把简单问题做复杂。你要一个导入功能，它可能给你设计任务队列、插件系统、事件总线、抽象适配层。看起来很专业，其实大部分是负债，导致上下文冗余。所以我现在在开发 prompt 里明确加两条原则：

使用剃刀原理：能不用的抽象就不用，能不加的配置就不加。  
使用第一性原理：从这个功能真正要解决的问题出发，不照搬惯例。

剃刀原理指的是：当有多个解释都能说明同一个现象时，应优先选择假设最少、最简单的那个解释。意思是不用引入不必要的复杂假设。从最基本、最确定、不可再拆的事实出发，重新推导问题，而不是直接套用经验、惯例或别人给出的结论。 第一性原理是马斯克经常说的一句话，指的是：从最基本、最确定、不可再拆的事实出发，重新推导问题，而不是直接套用经验、惯例或别人给出的结论。 剃刀原理解决的是别过度设计。第一性原理解决的是别盲目套模板。

很多时候 AI 会因为训练语料里大量项目都这么写，就默认你也需要这么写。比如：前端项目默认加状态管理；后端项目默认分 controller、service、repository等，但你的真实需求可能只是：读取一个文件，处理数据，输出结果。这时候最好的代码不是最像大项目的代码，而是最直接、最少、最好验证的代码。

### 示例 prompt

> 实现时遵守两个原则：
>
> 1. 剃刀原理：
>
> - 不添加当前需求没有用到的抽象。
>
> - 不添加未要求的配置项。
>
> - 不为了未来可能扩展而提前设计复杂结构。
>
> - 标准库能解决就不用新依赖，项目已有工具能解决就不用引入新工具。
>
> 2. 第一性原理：
>
> - 先说明这个功能的本质输入、处理过程、输出是什么。
>
> - 再基于现有代码结构选择最短实现路径。
>
> - 如果现有惯例和当前问题不匹配，指出原因，而不是机械照搬。
>
> 开始写代码前，先给一个简短实现方案，包括：
>
> - 要改哪些文件。
>
> - 为什么只改这些文件。
>
> - 如何验证。

这里的关键是让 AI 先解释本质输入、处理、输出。因为只要能它说清楚这个，很多复杂设计就自然消失了。

一个具体例子，有一次我做一个把 Markdown 文件里的标题提取出来生成目录的功能。一开始没有让他从剃刀原理和第一性原理角度考虑，他的方案就是：

1. 创建 parser 层；  
2. 创建 AST 抽象；  
3. 创建 heading service；  
4. 支持未来多格式；  
5. 预留插件接口；  
6. 引入 markdown-it。

当我在prompt里面添加了让他从剃刀原理和第一性原理角度考虑后，他的方案就简单很多：

1. 读取文本；  
2. 逐行匹配 `#` 开头的标题；  
3. 生成缩进目录；  
4. 写入或输出结果。

这时候你可以追问：

> 这个功能第一版只处理标准 Markdown 标题。请重新审视刚才方案，删掉所有不是当前需求必须的抽象。

这句话也是很有用的，它能让AI做精简，达到效果。

### 工程注意点

第一，简单不是粗糙。简单是每一行代码都能解释为什么存在。粗糙是靠侥幸跑通，不处理必要边界。

第二，不要把未来可能会用当成现在加代码的理由。未来真的来了，再重构。提前抽象最大的坏处是你还没看清问题，就先把结构固定了。

第三，让 AI 每次说明为什么只改这些文件。这能防止它到处乱碰。尤其是已有项目里，最怕它顺手格式化、顺手重构、顺手改一片。

## 03 — 开发完后，用对抗式审查审代码

AI 写完代码后，不要马上信。之前我会两种模型来交互审查，如gpt写的代码，让sonet4.6去审查，这点挺有效，如果你只有一种模型的话，可以试试对抗式审查。

对抗式审查不是普通 review，而是带着攻击性去找问题：

> 假设这段代码会在生产环境出事故，请你从反对者角度审查它。

这个环节非常重要。因为 AI 在写代码模式里，会天然维护自己的方案。你要让它切换到挑刺模式，它才会暴露更多问题。 对抗式审查的目标不是确认自己写得对，而是假设自己写错了，然后找证据。

它会检查：有没有边界条件漏掉； 有没有异常路径没处理；有没有安全问题；有没有并发或状态问题等。这其实是在模拟一个很严格的 code reviewer。

### 示例 prompt

> 审查时假设：
>
> - 这段代码会被真实用户使用。
>
> - 输入可能是脏数据。
>
> - 外部依赖可能失败。
>
> - 用户可能重复点击、刷新、中断流程。
>
> - 未来维护者不了解你刚才的上下文。
>
> 请重点找：
>
> 1. 可能导致功能错误的 bug。
>
> 2. 边界条件和异常路径。
>
> 3. 安全、权限、数据泄露风险。
>
> 4. 性能问题或资源泄漏。
>
> 5. 测试缺口。
>
> 6. 是否有过度设计或无关改动。
>
> 7. 是否违反项目现有规范。
>
> 输出格式：
>
> - 按严重程度排序。
>
> - 每个问题说明文件位置、原因、影响、建议修复方式。
>
> - 不要夸代码，只找问题。
>
> - 如果没发现问题，也要说明还剩哪些无法验证的风险。。

最后一句也很关键：

> 不要夸代码，只找问题。 我们不需要 AI 安慰。需要它帮我们省事故。

### 再进一步：让它自我反驳， 可以继续追问：

```
请站在一个不同意当前实现方案的资深工程师角度，提出 3 个最强反对意见。  
然后判断这些反对意见是否成立，如果成立，给出最小修改方案。
```

这个 prompt 经常能挖出隐藏问题。

### 工程注意点

第一，对抗式审查后，不要让它直接大改。先让它列问题，再决定哪些要修。否则它可能从一个过度实现跳到另一个过度修复。

第二，审查要结合 diff。最好让它基于本次改动审，而不是泛泛审整个项目。可以这样说：

```
只审查本次 diff 直接相关的代码，不要扩大范围做无关重构。
```

第三，审查后必须验证。AI 说修好了不算，测试过才算。哪怕只是跑一个最小命令，也比纯口头确认强。

## 04 — 我现在常用的一套完整流程

如果把上面三点串起来，我现在做 vibe coding 项目，基本是这个节奏：

第一步，先去 GitHub 找相似项目，分析可借鉴点和风险，不要写代码。

第二步，基于调研结果，定 MVP，用剃刀原理压缩第一版范围，只保留最小可用功能。

第三步，第一性原理说明输入、处理、输出，以及最短实现路径。写实现方案，不直接动手。

第四步，按方案实现，只改直接相关文件，不加未要求功能。再开始开发。

第五步，站在反对者角度审查本次 diff，只找问题，不夸代码，对抗式审查。

第六步，修复并验证，只修复审查中确认成立的问题，跑验证，说明结果。

这套流程看起来多了几步，但实际会更快。因为它减少了返工。AI 最耗时间的地方，不是写得慢，而是一开始写偏了以后要一点点拉回来。

结语

vibe coding 不是把需求丢给 AI，然后等它吐代码。更像是你带一个很快、很能干、但容易冲太猛的工程师做项目。我们要做的不是亲自写每一行代码，而是把关键判断点卡住：AI 越强，越不能只会说继续。真正有用的 prompt，不是让 AI 多写，而是让它在该停的时候停，在该想的时候想，在该删的时候删。
